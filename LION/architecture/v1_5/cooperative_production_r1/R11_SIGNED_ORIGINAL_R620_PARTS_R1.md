# R11 — independently signed original R6.20 input source

Status: SOURCE_ONLY_CANDIDATE / NOT_DEPLOYED / AUTHORITY_EFFECT=NONE.

The currently missing concrete R6.20 upstream twelve-part transport now
has a read-only consumer: cyber_lion.enterprise.r11_signed_original_r620_parts.
It consumes an existing privately preprovisioned SQLite table
r11_original_r620_signed_parts using the EXISTING original _ReadOnlySQLite
owner. Its columns and composite lookup coordinates are fixed:
(assignment_id, mission_id, generation, input_digest) primary key,
record_json, signature_hex and key_id. Neither a schema creation nor an
INSERT is implemented by this consumer; those effects belong to an
independent and separately approved original issuer/install/release.

Each canonical record contains exact repository, mission, worker,
assignment, generation, input digest, separate source identity/trust,
explicit original issuer subject + key ID, bounded issue/expiry times and
all twelve existing original R6.20 contract objects. Record data are
strictly canonical JSON; the reader denies duplicate keys, unknown fields,
nonfinite values, changed nested contract types, foreign identities,
past/future issuance, excessive lifetime and digest substitution.

Authentication is actual Ed25519 signature verification over a
domain-separated canonical byte string. The verifier public-key file is
direct, private and SHA-256 pinned from OUTSIDE the signed record; the
key ID and issuer subject are separately expected inputs, never selected
from the presented payload. The reader checks file owner/mode/inode,
trust binding and pinned key bytes at initialization and after each
lookup. No private key is accepted or constructed in the source. The
cryptography dependency already exists in requirements/edge-yoke.txt
for the original source/CI environment.

The original ReadOnlyOriginalR620EvidenceSource remains the downstream
consumer: it first checks exact canonical HELD assignment, original
operator/driver/revocation fences and source/trust identities; it then
calls this signed reader through resolve_exact(...), rebuilds the exact
OriginalR620PreparationParts, checks original R6.20 typed contracts and
reacquires independent canonical PDP/current policy. The original
R6.21 journal owner receives one bound trusted_now. No canonical
PDPResult or authority is signed/generated by this consumer; the
record must contain an already issued original PDPResult and the
separately issued canonical PDP store must agree.

The source-only integration test signs disposable fixture inputs using
a fresh in-memory Ed25519 test private key. Its verification and the
complete original R6.20->R6.21->R6.16->R6.17 MD001 preactivation test
prove correct byte/contract handling but NOT production signer identity,
real trust anchors, operator grants, RuntimeAdmission or deployment.
A SHA-256 pin proves exact key BYTES only; it cannot by itself establish
which original authority controls those bytes. A trusted independently
authorized original issuer, separately protected key distribution and
original signed R6.20 data creation pipeline are still missing live.

The exact original operator process must separately adjudicate the
prior PR #446 platform-security refusal, the consumed single-use
merge grant and protected R11 installation before any production
writer, MD001 canary or LPCL START. Code/CI/PR green are not authority.
