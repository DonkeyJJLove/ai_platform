# Epoch 3 → Epoch 4 control architecture

The Epoch 4 entry condition is operational rather than rhetorical: **LION MISSION CONTROL and LION CONTROL LPCL PANEL must become the normal control surface for autonomous evolution, while repository validation in `LION_EVOLUSION` remains the proof boundary.** The transition is a refactor of control semantics, not a replacement of safety boundaries.

At the end of Epoch 3 the control topology is: operator intent enters as LPCL; exact LPCL activation defines bounded mission scope; Mission Control owns mission lifecycle/currentness and database lineage; logical roles coordinate work; material executors provide bounded evidence/effects; local `gpt-oss-20b-MXFP4` remains proposal-only; `CHATGPT_SAAS_SUPERVISOR` remains an external-session-mediated supervisory reasoning plane until an automatic hop is independently materialized. Neither model is authority.

The control database is part of this topology. It stores the evolution of mission representations without rewriting history. A historical mission can be refreshed, audited and replay-designed. It can be restarted materially only through a compatible bounded adapter. A modern mission can be revised by creating a successor design revision. Adding a component means adding a typed component proposal and then, if execution is intended, compiling it into an exact LPCL and bounded adapter. Redesign is therefore a versioned state transition, not an in-place mutation of meaning.

Epoch 4 should begin with a separation between **mission lifecycle control** and **mission design evolution**. Lifecycle control covers currentness, start/stop/pause/resume/restart/validate where exact adapters exist. Design evolution covers add-component, redesign, semantic scaffold changes, new capability needs and successor mission generation. The latter remains `AUTHORITY_EFFECT=NONE` until compiled into a new exact LPCL and explicitly activated.

This creates the refactoring trajectory for later epochs: UI intent → typed mission action → database lineage/revision → semantic scaffold → capability gap → Bean/Composition/Abstraction materialization → exact LPCL/ActionSpec → authority/runtime admission → bounded effect → independent observation → reconciliation. The structure is deliberately recursive so the same control semantics can govern a component, a mission, a fleet or an architecture epoch.

The first Epoch 4 optimization track may then introduce semantic compilation without changing authority. Semantic Inference Compiler (SIC) is a future target, not an Epoch 3 AS-IS claim. It turns stable evidence-bound inference into reusable semantic structure so the system does not pay repeatedly for rediscovery. That target is compatible with Mission Control revisions: redesign and add-component requests become candidate inputs to semantic scaffolding, while currentness, provenance and effect admission remain separate.

### Entry gates

Epoch 4 may be declared only after: the four historical mission 404 defects are eliminated; schema-aware absence is visible; lifecycle actions and their fail-closed capability states are visible; current/recovery missions have a coherent execution binding; Mission Control DB migration is validated; control-plane rollback evidence exists; `127.0.0.1:8780` is actually listening and integrated rather than only documented as a target; the exact candidate passes the repository suite and effect-inventory validation; and the exact GitHub head/CI/publication state is reconciled. Until then the system remains in Epoch 3 closure.
